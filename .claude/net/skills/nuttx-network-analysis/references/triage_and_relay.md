## 一、前置分诊（进入决策树之前先做）

分析一个网络 Jira / 问题描述时，**先做下面两项快速分诊**，再进决策树。
目的：避免把"非 bug 的需求任务"当 bug 分析、避免漏掉"分支没同步"这一高频根因。

### 1.1 非 bug 快速识别

历史数据显示约 11% 的以太网 Jira 是功能需求 / 适配 / 同步任务，而非 bug。
进入正式分析流程前先判断是否为非 bug 类 issue，命中任一特征即判定为非 bug：

| 特征 | 示例 |
|------|------|
| summary 以 `[ETH]` 开头 + 无异常描述 | `[ETH]E2E P04/P05适配BMP`、`[ETH]MiRT支持json导入` |
| summary 含"适配/合入/同步/使能/升级" + 无失败现象 | `以太网BMP适配-工具`、`同步DEV到E3U1` |
| summary 含"bringup/开通/部署" | `TC4Z9 ETH ping bringup`、`eth功能部署到core1` |
| description 仅描述功能需求，无测试步骤/期望/实际现象 | `配置dfxlog输出syslog到ETH` |
| summary 含"整改/重构/优化" + 无 bug 现象 | `ETH代码注释打印整改`、`MiRT首版优化微重构` |

命中后输出，不进入分析流程：

```
📋 该 issue 为功能需求/适配任务，非 bug，不进入分析流程。
类型：{功能开发/分支同步/代码整改/功能适配}
建议：直接按开发任务处理，无需排查。
```

未命中 → 继续 1.2 分支同步检查 → 再进决策树。

### 1.2 分支同步检查（非主线分支 issue 必做）

历史数据显示约 15% 的以太网问题由分支同步遗漏导致（主线已修，E3→BMP/E3U1
等分支未 cherry-pick）。当 Jira 标题或描述含非主线分支标识（BMP/E3U1/E3U2/
Release 等）时执行：

1. 从 Jira 评论中搜索关键词：「未同步」「未合入」「patch未pick」「已修复」
2. 若问题在主线（如 dev-system）上已知已修复，检查当前分支是否含对应 patch：
   ```bash
   # 用 Gerrit commit message 关键词搜索当前分支是否包含修复
   git log --oneline --all --grep="{fix_keyword}" | head -5
   ```
3. 对比当前分支与主线的关键网络配置差异：
   ```bash
   grep -E "CONFIG_NET_|CONFIG_IOB_|CONFIG_TCP_|CONFIG_UDP_" .config | sort > /tmp/current_net.cfg
   # 若能拿到主线 .config，做 diff 对比
   ```

发现疑似遗漏时输出：

```
⚠️ 分支同步检查：当前分支可能缺少主线的修复 patch。
历史数据显示约 15% 的以太网问题由此导致。
建议：请研发确认主线上是否有对应修复，是否需要 cherry-pick。
```

> 此检查是 `rules/network-evidence-gate.md` 中「Step 2.2.2 分支同步检查」所指的
> 操作细节落点，属 gate 前的证据收集动作（不算源码定位，不受 gate 阻断）。

## 二、接力模式（Relay Mode，被 bug-analyze 接力调用）

当本 skill 被调用且提示中含 `[RELAY MODE]` 标记时（由 `bug-analyze` 统一入口在
问题分类路由后传入），按下表调整执行，其余分析步骤不变。目的：bug-analyze 已
完成的通用前置工作不重做，Jira 写操作统一交回 bug-analyze 收尾。

| 步骤 | 常规模式（直接调用） | 接力模式（bug-analyze 接力） |
|------|---------------------|------------------------------|
| Jira 拉取 | 自行拉取 | **跳过**：复用 `.vela_bug/{JIRA_ID}/jira_info.md` + 已下载附件；缺失则回退自行拉取 |
| 非 bug 快速识别（§1.1） | 执行 | **跳过**（bug-analyze 路由阶段已判定为网络 bug 才会 relay 进来） |
| 平台/.config/ELF 环境准备 | 执行 | 执行（不变） |
| 证据门 + 经验前置匹配 | 执行 | **照常执行，不豁免**（见 `rules/network-evidence-gate.md`） |
| 根因门 | 执行 | **照常执行，不豁免**（见 `rules/network-root-cause-gate.md`） |
| 分析与 CP 确认 | 执行 | 执行（不变） |
| 代码修复 + 板级验证 | 执行 | 执行（编译/烧录/Gerrit 由 `module-dev` 编排） |
| 经验沉淀（network-bug-card 模式 B） | 执行 | 执行（经验闭环不交回） |
| Jira comment / 状态流转 / Resolve | 执行 | **跳过**（全部交 bug-analyze 收尾） |

**输入契约（bug-analyze → 本 skill）**：relay 时上游应已提供
- `.vela_bug/{JIRA_ID}/jira_info.md`（结构化 Jira 信息）+ 已下载附件（日志/pcap/截图）
- Gate 1 经验匹配结果（命中卡 id + 置信度，可能为空）
- 执行模式（标准/快速/仅分析）

**回传契约（本 skill → bug-analyze）**：产出结论后回传
- 根因描述（Gate 2 经验提取输入）
- 修复方案 + Gerrit 链接
- 关键纠偏点

**接力完成标志**：产出分析结论后输出一行交回控制权：

```
✅ [RELAY] network 接力分析完成，结论已生成，控制权交回 bug-analyze
```

> 路由按**调用栈内容**分流，不是"有没有 crash"：crash 且调用栈含网络函数
> （`tcp_*`/`iob_*`/`can_*`/`enet_*`/`arp_*` 等）→ 归网络，relay 进本 skill 走
> Crash 流程；只有纯系统栈（mm/sched 等无网络函数）的 crash 才由 bug-analyze 交
> crash-analysis。理由：网络 crash 根因多在网络逻辑（IOB UAF / ifdown 竞态 /
> DMA 越界），通用 crash 池查不到这些。
>
> 现状说明：bug-analyze 的问题分类路由层若尚未落地，`[RELAY MODE]` 可能暂无调用方；
> 本节为接入就绪的接口规格，独立调用本 skill 时不受影响。

## 三、能力边界与弱项信息补充清单

用于在信息不足时主动喊停、要数据，而不是硬猜根因。

### 3.1 能力自评

| 能力 | 问题类型 | 独立定位概率 |
|------|---------|------------|
| ✅ 强 | 配置宏未使能 / 分支同步遗漏 / 端口范围 / 输入物适配 | 85-92% |
| ✅ 强 | NuttX 协议栈源码分析（TCP/iob/ICMP/ARP） | ~90% |
| ✅ 强 | Crash 分析（有调用栈/coredump） | ~90% |
| ✅ 强 | CAN 驱动源码 / IOB 池配置 / CAN ifup/ifdown 生命周期 | 70-90% |
| 🟡 中 | 驱动问题（DMA/I2C/PHY/中断/MAC） | ~88%（需评论中有根因线索） |
| 🟡 中 | 应用层模块（MiRT/SocketMgr/DoIP/EthTsyn 等，仅 CarOS） | 60-75% |
| 🟡 中 | ETH-CAN 路由丢帧/时延、BMP 模式 CAN 适配、CAN 发送鲁棒性 | 40-70% |
| 🟡 中 | 测试环境（脚本/配置可分析，台架/硬件不可） | 20-40% |
| 🔴 弱 | 性能问题（吞吐/CPU/中断响应） | ~50%（需设备侧 profiling） |
| 🔴 弱 | 偶发问题（无 crash 无异常日志） | ~0%（需复现环境） |
| 🔴 弱 | 设计预期类（时钟精度/ICMP 过滤策略） | ~0%（需产品规格文档） |

🔴 弱项问题应在初步判断中明确标注所需信息，不硬猜。

### 3.2 信息不足时的补充清单

> 前置条件：输出此清单前，必须确认已完成自主分析——应用层调用了 NuttX API
> （`send()`/`recv()`/`ioctl()`）时先追踪其在协议栈内的完整路径；相关源码可读时
> 先读完再判断。**仅在协议栈路径已追踪完毕、仍无法定位时才输出此清单。**

```
【ETH 不通 / link down】
☐ 串口日志（含启动阶段 ETH 初始化打印）
☐ 设备电流值（异常偏低可能是 Switch 未上电）
☐ ifconfig 输出（网口是否 UP/RUNNING）
☐ PHY 寄存器状态（link/speed/duplex）

【Crash / Coredump】
☐ 完整 crash 日志（PC/SP/调用栈/Trap 类型）
☐ coredump 文件 + 对应 ELF 路径

【功能异常（路由/协议/时钟）】
☐ 观测量截图（相关计数器/状态值）
☐ 报文日志（.blf / pcap）
☐ 对比正常版本的差异（哪个版本是好的）

【性能问题】
☐ CPU 占用率（各核 idle 百分比）
☐ 中断统计、DMA 描述符使用率（RX/TX used/total）
☐ 吞吐测试数据（iperf / 打流结果）

【偶发问题】
☐ 复现概率 + 复现步骤
☐ 是否重跑能过
☐ 环境差异对比（哪些台架复现、哪些不复现）
```

### 3.3 测试环境 vs 软件问题的判别线索

| 线索 | 判断方向 |
|------|---------|
| "换台架后正常" / "其他台架不复现" | 大概率环境问题 |
| "同一软件在 VTx 正常在 VTy 异常" | 大概率环境问题 |
| "刷最新软件异常，回退旧版本正常" | 大概率软件问题 |
| "必现 + 所有台架都复现" | 大概率软件问题 |
| 电流偏低 | 大概率 Switch 未上电（硬件/I2C） |
| 标题含"测试脚本问题" | 直接归类为测试环境 |

无法判断时输出补充建议（换台架复现 / 回退版本对比 / 检查台架连接与 Switch 固件），不硬下结论。
