## 1. 周期任务 runningtime 超预期（中断负载高）

**特征**：core0 1ms 任务实际 1900us，10ms 任务实际 11200us，中断占用过高（13088）

**排查步骤**：
1. 用 `cat /proc/irqs` 或 trace 工具统计各中断的触发频率和处理耗时
2. 检查 CAN 接收中断是否因高负载导致频繁触发
3. 检查 hpwork 队列积压情况 -- 中断 bottom half 是否排队过长
4. 考虑将 CAN 收包中断处理移到独立的高优先级任务或调整中断亲和性

## 2. eth2can 路由时延超标

**特征**：全量通信负载下 eth2can 路由时延超过 1.5ms 指标（15419）

**排查步骤**：
1. 用 trace 分析路由路径各阶段耗时：ETH 收包 -> 路由查表 -> CAN 发送
2. 检查是否有优先级反转 -- 路由任务被低优先级任务间接阻塞
3. 检查 IOB 分配是否因池不足导致等待
4. 对比 BMP 和 AMP 模式下的时延差异


## 3. BMP 模式 eth 中断 work 激活慢

**特征**：BMP 模式 eth2can 负载下中断执行次数比 AMP 少一半，耗时 1.5 倍（16171）

**排查步骤**：
1. 检查 BMP 模式下中断亲和性配置 -- 中断是否被分配到负载最高的核
2. 检查 work_queue 调度优先级在 BMP 下是否被其他 BMP 调度实体抢占
3. 对比 BMP/AMP 的中断响应延迟（从中断触发到 work 执行的时间差）
4. 检查是否有不必要的锁争用导致中断 bottom half 排队

---

## 4. ICMP 响应延迟过高

**特征**：ping 响应时间远超预期（如 >10ms），或偶发性延迟抖动大

**排查步骤**：
1. 检查 ICMP 处理是否在 hpwork 队列中被高优先级任务阻塞
2. 检查网络中断到 ICMP reply 发出的完整路径是否有不必要的调度延迟
3. 检查 IOB 分配是否因池不足导致等待
4. 对比空载和满载下的 ping 延迟差异——确认是否为负载导致
