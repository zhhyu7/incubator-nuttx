## 1. TCP 连接超时/重传过多/RST

### 1.1 TCP 连接超时

**特征**：`connect()` 返回 ETIMEDOUT

**排查思路**：
1. 检查 ARP 解析是否成功
2. 检查路由是否正确
3. 检查 PHY 链路是否 up
4. 检查 SYN 重传次数和间隔
5. 检查对端是否可达

### 1.2 TCP 重传过多

**特征**：通信正常但性能差，网络统计显示大量重传

**排查思路**：
1. 检查 RTT 估算是否合理
2. 检查拥塞窗口大小
3. 检查网络丢包率
4. 检查 MTU 是否匹配（避免分片）
5. 检查 SACK 是否启用

### 1.3 TCP 连接 RST

**特征**：连接被意外重置

**排查思路**：
1. 检查对端是否主动发送 RST
2. 检查 TCP 超时配置
3. 检查 IP 过滤/NAT 规则
4. 检查 Keepalive 配置

## 2. TCP 发送缓冲区信号量竞态

> ⚠️ **修复状态提示**：此问题有明确的单字符修复方案。排查前请先检查当前代码中发送缓冲区通知函数的条件判断是否已修复。

**特征**：TCP 高吞吐发送（如 iperf client）运行一段时间后永久卡死，调用栈卡在发送信号量等待。ping 正常，链路正常，IOB 正常，驱动正常。

**原理**：发送缓冲区通知函数中，信号量值检查条件不完备。在"释放锁"到"执行 sem_wait"之间存在竞态窗口：高优先级 workqueue 线程在此窗口内抢占并释放 write buffer，但因信号量值为 0（而非负数）不执行 post，导致信号丢失。发送线程恢复后永久阻塞。

**竞态时序**：
```
发送线程 (低优先级)                    workqueue (高优先级)
──────────────────                    ──────────────────
while(inqueue >= limit) → true
sem_timedwait 准备:
  breaklock 释放 dev 锁
  ─── 被抢占 ──────────────→         拿到 dev 锁
                                      eventhandler: ACK, 释放 wrb
                                      notify: val = 0, 不 post ❌
                                      释放锁
  ←── 恢复执行 ────────────
  sem_wait(...)
  ... 永远阻塞 ...
```

**死局**：信号丢失后形成循环死锁——需要 notify 唤醒 → 需要新 ACK 触发 notify → 需要发新数据收 ACK → 需要唤醒才能发新数据。

**修复**：通知条件从 `val < 0` 改为 `val <= 0`。

**影响范围**：所有启用发送缓冲区大小限制的 TCP 高吞吐发送场景。即使不完全卡死，竞态命中也会导致发送流水线断流（等待下一次 TCP poll），显著降低带宽。

**排查思路**：
1. 确认调用栈卡在发送信号量等待
2. 确认 ping 正常、IOB 正常、驱动正常（排除其他原因）
3. 检查通知函数中的信号量值判断条件

## 3. TCP nrtx 重传计数累计断连

**特征**：负载工况下 TCP 连接约 5 分钟后断连

**原理**：TCP 协议栈的重传计数在持续发送场景下不清零，累计达到重传上限后认为超时，主动断开连接。

**典型案例**：VELAFORCAR-15435

**排查思路**：
1. 检查 TCP 断连时重传计数是否达到上限
2. 检查重传计数的递增和清零逻辑
3. 检查是否在收到 ACK 时正确清零了重传计数
4. 检查 write buffer 持续发送场景下的重传计数行为

**修复方向**：
- 在 TCP 发送确认（ACK 收到）时正确清零重传计数

## 4. UDP 丢包/端口绑定/广播多播

### 4.1 UDP 丢包

**特征**：部分 UDP 包丢失，无错误返回

**排查思路**：
1. 检查 IOB 可用数
2. 检查接收缓冲区大小
3. 检查发送速率是否超过处理能力
4. 检查中断处理是否及时
5. 检查 DMA RX 描述符是否充足

### 4.2 UDP 端口绑定失败

**特征**：`bind()` 返回 EADDRINUSE 或 EACCES

**排查思路**：
1. 检查端口是否已被占用
2. 检查 SO_REUSEADDR 选项
3. 检查端口范围配置

### 4.3 UDP 广播/多播

**排查思路**：
1. 检查 SO_BROADCAST 选项是否设置
2. 检查 IGMP/MLD 配置（多播）
3. 检查网络接口是否支持多播

## 5. TCP 挥手少发 FIN,ACK

**特征**：对端发 FIN,ACK → 本端只回 ACK，不回 FIN,ACK → 挥手异常

**典型案例**：VELAFORCAR-15457 / 15711 / 15990 / 15470

**排查思路**：
1. 确认是应用层还是协议栈的问题
2. 检查应用层是否在收到对端 FIN 后调用了 close()
3. 如果应用层没调用 close() → 应用层问题
4. 如果调用了 close() 但协议栈没发 FIN → 检查 TCP close/send 逻辑

## 6. TCP 重传次数不符合企标

**特征**：TCP SYN 重传或数据段重传次数比规范要求少一次

**典型案例**：VELAFORCAR-15622 / 13495 / 15349

**排查思路**：
1. 检查重传上限配置（数据重传和 SYN 重传分别配置）
2. 对比规范要求的重传次数
3. 注意协议栈的重传计数起点（可能从 0 开始，实际重传 N 次但计数器显示 N-1）

## 7. TCP 端口号范围异常

**特征**：外发 TCP 报文的源端口号超出规范规定范围

**典型案例**：VELAFORCAR-15989 / 15475 / 15350

**排查思路**：
1. 检查临时端口范围配置（min/max port）
2. 对比规范要求的端口号范围
3. 修改 Kconfig 配置即可

## 8. TCP 断连后 SYN 无响应

**特征**：非法请求导致 TCP 断连后，新的 SYN 请求无响应

**典型案例**：VELAFORCAR-15429

**排查思路**：
1. 检查连接关闭后是否正确释放了资源（conn/IOB）
2. 检查 TIME_WAIT 状态是否阻止了新连接
3. 检查 TIME_WAIT 超时配置

## 9. USRsock 跨核发包阻塞调度

**特征**：USRsock 跨核发包阻塞低优先级调度任务

**原理**：USRsock 通过 RPMSG 通道跨核发包时，如果 RPMSG 通道缓冲区满，发送方会阻塞等待。高优先级调度任务中如果包含 USRsock 发包操作，会导致该任务阻塞。

**典型案例**：VELAFORCAR-13547 / 13518

**排查思路**：
1. 检查 USRsock RPMSG 发送是否为同步阻塞调用
2. 检查 RPMSG 通道的缓冲区大小和流控机制
3. 解决方向：异步发送、增大 RPMSG 缓冲区、或将网络发包移到低优先级任务

## 10. TCP 多连接建立失败

**特征**：作为 TCP server 创建多个连接，后几个无法建联

**典型案例**：VELAFORCAR-14206 / 15522

**排查思路**：
1. 检查预分配连接数配置
2. 检查监听队列大小配置
3. 如果预分配连接数不够，新连接分配失败
4. 检查是否有连接泄漏（旧连接未正确关闭）

## 11. TCP Keepalive 未发出

**特征**：TCP 长连接超时后未发出 keepalive 报文

**典型案例**：VELAFORCAR-13562

**排查思路**：
1. 检查 keepalive 功能是否在 Kconfig 中启用
2. 检查应用层是否设置了 SO_KEEPALIVE socket 选项
3. 检查 keepalive 参数（idle time / interval / count）

## 12. TCP 高吞吐打流异常

**特征**：TCP/UDP 高吞吐打流时 coredump 或收包速率突然降为 0

**典型案例**：VELAFORCAR-7214 / 6997 / 3475

**排查思路**：
1. 检查 IOB 配置是否足够（总数 × 单个大小）
2. 检查 DMA RX 描述符数量（高吞吐需要更多描述符）
3. 检查 DMA 中断是否正常触发
4. 检查 TCP 接收窗口大小是否匹配吞吐量
5. coredump 场景需要 GDB 分析调用栈
