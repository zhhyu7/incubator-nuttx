## 1. IOB 耗尽与泄漏

**特征**：发送返回 ENOBUFS，IOB 状态显示可用 IOB 为 0 或持续减少

### 1.1 IOB 配置不足

- IOB 总数配置过小
- 多个网络接口竞争 IOB 资源
- TCP 接收窗口过大占用大量 IOB

### 1.2 IOB 泄漏

- 协议栈异常路径未释放 IOB
- 驱动 TX 完成回调未正确释放
- 错误处理分支遗漏 IOB 释放

### 1.3 IOB 诊断方法

```bash
# 查看 IOB 状态
cat /proc/iob

# 搜索 IOB 分配/释放日志
grep -E "iob_alloc|iob_free|iob_navail" <日志>

# 检查 IOB 相关配置（从 .config 中搜索，具体配置项名称以知识库或源码为准）
grep -E "IOB" <.config_path>
```

## 2. net_lock 死锁

**特征**：网络任务挂起，系统部分功能正常但网络完全不通

### 2.1 中断上下文中使用可睡眠锁

**原理**：网络全局锁可能导致睡眠，不能在中断上下文中调用。

**排查思路**：检查中断处理函数（Ethernet/RPMSG）中是否直接或间接调用了可睡眠的锁获取。

### 2.2 嵌套锁获取

**原理**：同一线程重复获取同一锁、或多把锁的嵌套顺序不一致会导致死锁。

**排查思路**：
1. 检查是否有同一线程重入获取网络锁
2. 检查网络锁与其他锁（驱动锁等）的嵌套顺序是否全局一致

### 2.3 持锁后阻塞

**原理**：持有网络锁后等待资源（如 IOB 分配）或等待硬件完成（如 DMA），如果这些操作可能阻塞，就形成了死锁条件。

**排查思路**：
1. 检查持锁路径中是否有可能阻塞的 IOB 分配
2. 检查持锁路径中是否等待 DMA 完成

### 2.4 诊断方法

```bash
# 检查任务状态
ps -l

# 查看网络锁相关日志
grep -E "net_lock|net_unlock|net_sem" <日志>

# 检查是否有任务长时间等待
cat /proc/<pid>/status
```

## 3. 多核网络初始化 Crash

**特征**：非 CPU0 核心启动阶段崩溃，调用栈涉及网络设备注册 → IOB 可用数查询

### 3.1 IOB/Mempool 初始化顺序

**原理**：IOB mempool 使用 lazy init 机制——首次访问时才初始化。如果非 CPU0 核先于 CPU0 访问 IOB，会触发对未初始化资源的操作。

**排查思路**：
1. 确认 IOB 初始化是否在所有核启动前完成
2. 检查 lazy init 路径中的同步保护
3. 检查多核启动顺序是否保证了共享资源先初始化

### 3.2 网络设备注册时序

**原理**：网络设备注册时会查询 IOB 可用数（CAN 设备还有特殊的 buffer size 查询），这会触发 mempool 的 lazy init。多核同时注册网络设备时可能竞争。

**排查思路**：
1. 确认各核网络设备注册的调用顺序
2. 检查是否有同步机制确保初始化完成后再允许注册

## 4. per-CPU 变量 BMP 适配问题

**特征**：BMP 多核架构下启动 crash + 堆管理 assert 失败

**原理**：per-CPU 变量宏名拼写错误时，宏替换不生效，所有 CPU 操作同一份数据。CPU1 释放 CPU0 堆区内存时触发 assert。

**典型案例**：VELAFORCAR-16242

**排查思路**：
1. 检查 crash 调用栈是否涉及堆管理或 mempool 函数
2. grep per-CPU 变量宏定义，确认拼写是否正确
3. 检查 BMP 模式下全局变量是否正确使用了 per-CPU 包装
4. 检查静态 pool buffer 声明是否区分了各核

**修复方向**：
- 修复 per-CPU 变量宏名拼写
- 删除 BMP 模式下不需要的全局 pool 别名
- 使静态 pool buffer 声明区分各核

## 5. 多核竞争排查指南

### 日志关键字

```bash
# 网络锁相关
grep -E "net_lock|net_unlock|NET_LOCK|net_sem" <日志>

# 自旋锁相关
grep -E "spin_lock|spin_unlock|irqsave|irqrestore" <日志>

# UAF 特征（mempool free 魔数，需从源码确认当前值）
grep -E "already freed|double free|use.after.free" <日志>

# IOB 相关
grep -E "iob_alloc|iob_free|iob_navail|IOB" <日志>
```

### 多核竞争证据模式

1. **同一 IOB 被多核访问**：
   - 两个核的日志中出现同一内存地址的 IOB 操作（一个释放、一个仍在使用）

2. **锁获取顺序不一致**：
   - 核 A: 网络锁 → 驱动锁
   - 核 B: 驱动锁 → 网络锁（死锁风险）

3. **中断与线程竞争**：
   - 中断上下文操作 IOB → 同时线程释放同一 IOB → io_offset 被覆写为 free 魔数（UAF）

## 6. CAN 驱动 IOB Use-After-Free

**特征**：
- io_offset 被覆写为 mempool free 魔数
- 错误地址在 IOB buffer 范围内

**排查思路**：

### 6.1 CAN TX 路径 IOB 生命周期

- 发送函数中 IOB 分配后是否正确传递给驱动
- 驱动发送完成后 IOB 是否被正确释放（而非重复释放）
- TX 完成回调中是否存在重复释放

### 6.2 CAN RX 路径 IOB 生命周期

- 驱动收包分配的 IOB 是否正确传递给上层
- 协议栈处理后 IOB 归属是否明确
- 多个 socket 接收同一帧时的 IOB 克隆问题

### 6.3 多核竞争导致的 IOB 状态混乱

- 一个核释放 IOB 时另一个核仍在使用
- 中断上下文与线程上下文的竞争

---

### 6.4 CAN TX 失败

**特征**：sendmsg 返回负数值，errno 可能为 ENOBUFS、EAGAIN、EIO 等

**排查思路**：

1. **驱动层**：TX FIFO/Queue 满、TX 事件 FIFO 溢出未处理
2. **硬件配置**：波特率/时序、TX Buffer 元素大小与 CAN FD 数据长度匹配、Message RAM TX 区域配置
3. **协议栈**：IOB 分配失败、网络设备未正确 up、TX 通知未能触发驱动发送
4. **总线状态**：无其他节点（无 ACK）、Bus-Off 未恢复、错误计数器超限

---

### 6.5 CAN RX 异常

**特征**：收到的帧数据内容错乱，或完全收不到报文

**排查思路**：

1. **驱动层**：从 Message RAM 读取数据的逻辑、RX FIFO 溢出导致丢帧、RX 中断处理 bug
2. **硬件配置**：RX Filter 配置（标准/扩展 ID）、Message RAM RX 区域配置、RX FIFO 水位与中断触发条件
3. **协议栈**：数据拷贝错误、CAN 过滤器配置不当、多 socket 绑定同一设备时的分发逻辑
4. **多核竞争**：RX 中断与应用层 recvmsg 的竞争、IOB 链表操作的原子性

---


### 6.6 多核 CAN 驱动初始化 Crash

**特征**：
- Crash 发生在非 CPU0 核心的启动阶段
- 调用栈涉及网络设备注册 → IOB 查询 → mempool 操作
- 错误地址可能指向 mempool 结构体

**原理**：CAN 设备注册时会触发特殊的 IOB 查询（按 buffer size 查询可用数），这是 CAN 特有的行为。如果 mempool 尚未初始化（lazy init），在多核同时注册时会触发竞态。

**排查思路**：

1. **IOB/Mempool 初始化顺序**：
   - IOB mempool 使用 lazy init
   - 如果非 CPU0 核先于 CPU0 访问 IOB，可能触发未初始化的自旋锁
   - 确认 IOB 初始化是否在所有核启动前完成

2. **CAN 驱动多核初始化时序**：
   - 检查各核 CAN 初始化函数是否使用 coreid 过滤
   - 检查初始化调用顺序和多核同步机制

**CAN 设备注册时的特殊行为**：

CAN 网络设备注册时会查询特定 buffer size 的 IOB 可用数（其他设备类型只查询总可用数），这是触发 mempool lazy init crash 的直接原因。

**排查建议**：
- 确认 IOB 初始化的调用位置和时机
- 确认 CPU0 完成所有共享资源初始化后，其他核才开始初始化
- 考虑在 CAN 驱动初始化前添加 IOB 就绪检查

## 10. net_lock 死锁导致调度停止

**特征**：startup 阶段多个任务均阻塞在网络锁，调度完全停止

**原理**：启动阶段如果某个任务持有网络锁后调用了需要再次获取网络锁的函数（重入死锁），或依赖另一个需要网络锁的任务完成（循环等待），会导致所有网络相关任务阻塞。

**典型案例**：VELAFORCAR-14288

**排查思路**：
1. 检查启动阶段是否在持有网络锁时调用了需要网络锁的函数
2. 检查工作队列任务是否因等待网络锁而无法执行其他关键初始化
3. 用 coredump 分析各任务的等待链：哪个任务持有 lock，哪些任务在等待
4. 关注启动顺序——各网络子系统的初始化是否有隐含的依赖关系


## 8. SIL 高概率软件卡住

**特征**：SIL 环境高概率测试执行时软件卡死，外发报文一段时间后停止

**原理**：SIL 环境调度时序与真实硬件不同，竞态窗口更大。可能是资源泄漏或虚拟驱动行为不一致导致。

**典型案例**：VELAFORCAR-13077

**排查思路**：
1. 检查虚拟驱动的定时器/事件模拟是否与实际硬件一致
2. 检查是否有资源泄漏（IOB/socket/fd）
3. 用 `ps` 查看各任务阻塞点
4. SIL 偶发问题优先关注竞态条件
